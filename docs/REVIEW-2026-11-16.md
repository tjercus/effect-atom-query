## 1. Logical errors

| #   | Severity | Status | Finding                                                                         |
| --- | -------- | ------ | ------------------------------------------------------------------------------- |
| 1   | High     | fixed  | `client.clear` inside a mutation's own callback kills that mutation             |
| 2   | High     | fixed  | `fetchQuery` fails with `InterruptError` when another caller supersedes a fetch |
| 3   | Medium   | fixed  | An interrupted mutation is reported as a defect, against decision D7            |
| 4   | Medium   | 1.2.1  | Closing the client re-creates entries and refetches through the atom path       |
| 5   | Medium   | fixed  | `resetQueries` leaves an observed `staleTime: "static"` query pending forever   |
| 6   | Medium   | fixed  | `initialData` beats restored persisted data                                     |
| 7   | Low      | fixed  | One query atom in two registries: `refresh` hits the wrong client               |
| 8   | Low      | fixed  | A per-observer `staleTime` never triggers a re-render                           |
| 9   | Low      | fixed  | Entry leak after `resetQueries` interrupts an unobserved fetch                  |
| 10  | Low      | fixed  | Keys with `undefined` properties split in the cache but collide in storage      |

### 1. `client.clear` inside a mutation's own callback kills that mutation [probe]

`clear` called `mutationCache.clear()`, which disposed every execution and
interrupted its fiber, including the one whose callback was calling `clear`.
`onExit` then returned early because the entry was already removed.

```ts
const logout = Mutation.make({
  run: () => Effect.succeed("bye").pipe(Effect.delay("1 second")),
  onSuccess: () => QueryClient.QueryClient.pipe(Effect.flatMap((c) => c.clear)),
});
```

Observed: code after `clear` never ran, the definition's `onSettled` was
skipped, the UI callbacks never fired, `useMutation` stayed `pending`, and
`client.mutate` failed with `InterruptError`. This is the usual logout flow.

### 2. `fetchQuery` fails with `InterruptError` when a fetch is superseded [probe]

`fetchQuery`, `prefetchQuery` and `ensureQueryData` joined the entry's shared
fetch fiber. A concurrent `invalidateQueries` (which supersedes a running
fetch when the query has data) interrupted that fiber, and the caller failed
with an interrupt that is not part of `E`, so `Effect.catch` cannot handle it.
A route loader failed because a mutation elsewhere invalidated the query.

`cancelQueries` and `removeQueries` interrupt the caller in the same way.
That part is kept: an explicit cancellation is an interruption. See the fix
notes below.

### 3. An interrupted mutation is reported as a defect [probe]

`run: () => Effect.interrupt` gave `status: "error"` with
`MutationResult.isDefect === true`. `useMutation` throws defects to the error
boundary, and the observer's `onError` fired with an interrupt cause.
Decision D7 says interrupt-only causes never reach `error`, error boundaries
or `onError`. Queries complied; mutations did not.

### 4. Closing the client re-creates entries through the atom path [probe]

The earlier fix for "closing the client does not re-create observed entries"
covered `QueryObserver` only. The query atom's reader called
`get.refreshSelf()` whenever its entry was removed, so a mounted atom rebuilt
its entry on the disposed cache and ran `run` a second time on a closed
client.

### 5. `resetQueries` on an observed static query [probe]

`reset()` drops the data, then `refetchEntries` filters out queries with
`staleTime: "static"` (`QueryClient.ts`, `refetchEntries`). Nothing refetches
until the component remounts: the query shows `pending` / `idle`.

### 6. `initialData` beats restored persisted data [probe]

The entry constructor seeds `initialData` first; `claimPersisted()` then
returns early because data exists. The restored value is never used and stays
in `runtime.preloaded`, so it is written back to storage until `maxAge`.

### 7. One atom in two registries [probe]

`Query.makeAtom` keeps the entry of the latest build in a closure per atom,
not per registry. With the same atom mounted in registries A and B,
`registryA.refresh(q)` refetched B's entry. This affects tests and
multi-client setups.

### 8. Per-observer `staleTime` [probe]

The stale timer uses the entry's `staleTime` only. With an entry at
`"1 hour"` and an observer at `"5 seconds"`, `isStale` is correct when read
but no notification fires when the observer's threshold passes.

### 9. Entry leak [probe]

With no observers, the gc timer can fire during a fetch and skip removal. If
`resetQueries` then interrupts that fetch, `onFetchExit` is ignored (the
fetch id was bumped) and gc is never rescheduled.

### 10. `undefined` in keys [probe]

`["p", { a: undefined }]` and `["p", {}]` are different cache entries, but
`QueryKey.toJsonKey` returns the same string for both, so two persisted
entries overwrite each other.

## 2. Forgotten edge cases

All **[read]**.

- A `select` that throws crashes the render (`QueryObserver.select`). Nothing
  catches it, so it reaches the error boundary instead of an error result.
- `meta` is unreachable. Its doc comment says "available to filters'
  predicates", but a predicate receives `{ key, result }` only. Only the
  devtools read it.
- Hook-level `useMutation` callbacks are dropped when the component unmounts
  or a newer `mutate` starts. This is documented, but a "mutate, then navigate
  away" flow loses its toast.
- Persistence failures are silent: decode errors in `claimPersisted`, encode
  errors in `snapshot`, and store write errors in `QueryPersister.layer` are
  swallowed without a log or a hook. A full quota or a schema change is
  invisible.
- `QueryClientProvider` reads the client with `runtime.runSync`. Any
  asynchronous layer (a blocking restore from IndexedDB, for example) throws
  on the first render.
- `setQueryDefaults` re-resolves the options of live entries but does not
  reschedule their gc, stale or polling timers.
- `removeQueries` ignores the `stale` and `fetchStatus` filters when it drops
  unclaimed restored data.
- A query entry built on a cache that is already disposed (a component that
  mounts after the client closed) still fetches. The fix for finding 4 covers
  re-attachment only.

## 3. Migration usability

### From TanStack Query

- **`R` is not checked for hooks.** `useQuery` ignores `R`, and the provider
  accepts `ManagedRuntime<QueryClient, any>`. A missing service compiles and
  then dies at runtime into the error boundary. A typed hooks factory
  (`makeHooks<R>()`) or a generic provider would close this.
- **Imperative calls need the runtime imported in every component**
  (`runtime.runFork(client.invalidateQueries(...))`). A hook bound to the
  provider's runtime would remove most of that.
- **`refetch`, `fetchNextPage` and `fetchPreviousPage` return `void`**, so a
  handler cannot wait for the result.
- **`invalidates` always waits for the refetches**, including the query's
  three default retries. This is documented, but there is no way to opt out.
- **Two key differences are missing from the guide**: the first element must
  be a string, and `{ a: undefined }` does not equal `{}`.
- **`docs/FEATURE-MATRIX.md` overstates.** It marks `fetchInfiniteQuery`,
  `prefetchInfiniteQuery`, `ensureInfiniteQueryData` and `mount` / `unmount`
  as done; none of them exist on the client. It names `Schedule.either` where
  the code uses `Schedule.min`.
- **The README status is stale**: it says "pre-release (0.x), not yet
  published" while the packages are at 1.2.0.

### From RTK Query

The repository does not mention RTK Query at all: there is no guide and no
mapping table.

Mappings that work today and are worth documenting:

| RTK Query           | effect-atom-query                        |
| ------------------- | ---------------------------------------- |
| `skipToken`         | `Query.skipToken`                        |
| `pollingInterval`   | `refetchInterval`                        |
| `keepUnusedDataFor` | `gcTime`                                 |
| `selectFromResult`  | `select`                                 |
| `onQueryStarted`    | `onMutate` / `Mutation.optimisticUpdate` |
| `fixedCacheKey`     | the mutation atom itself                 |
| `.unwrap()`         | `mutateEffect`                           |
| `invalidatesTags`   | `invalidates` / `reactivityKeys`         |

Missing from the API:

- a lazy query hook, or any trigger whose result can be awaited;
- a streaming cache-entry lifecycle (`onCacheEntryAdded`-style updates);
- per-result tags (`providesTags` with ids): only key prefixes exist;
- invalidation on failure: `invalidates` runs on success only;
- an endpoint or code generation story.

## 4. Effect coding standards

The repository has no rules file (`AGENTS.md`,
`.specify/memory/constitution.md` and `.github/instructions/` are absent), so
the yardstick is general Effect v4 convention.

- **Effect diagnostics do not run.** `effect-language-service` refuses
  TypeScript 7 and points to `@effect/tsgo`. A passing `vp check` says nothing
  about floating Effects and similar mistakes. The tracked item of decision
  D10 can be acted on now.
- **No tracing.** There are no spans around fetches or mutations.
  `Effect.withSpan` with the key as an attribute would show every query in a
  tracer.
- **Unstructured concurrency.** Every fiber is started with `runFork` and
  stopped with `interruptUnsafe`, tracked in class fields. Findings 1, 4 and 9
  are lifecycle bugs of that design. `FiberSet` / `FiberMap` tied to the
  client's scope would remove the class.
- **Plain `Error` subclasses** (`MissingQueryClientError`,
  `MissingQueryClientProviderError`) instead of `Data.TaggedError`.
- **`try` / `catch` around synchronous Schema calls**, where
  `Schema.decodeUnknownOption` (already used in `QueryPersister.ts`) and a log
  line would do.
- **Internals on the public service**: `cache`, `mutationCache` and `runtime`
  are on `QueryClient.Service`, marked `@internal`, and the React package
  depends on them.
- **No `dual` APIs**: `QueryResult.map`, `QueryResult.match` and
  `QueryKey.matches` are data-first only, so they do not pipe.
- **In line with convention**: `Context.Service` / `Context.Reference`, a
  scoped `Layer`, the captured `Clock` (so `TestClock` works everywhere),
  `Schedule` for retries, `Option` throughout, and `it.effect` tests.

## 6. Fix notes

- **1.** `QueryClient.clear` (and gc) now only drop mutation executions from
  the cache: a running execution finishes, its callbacks run, and its
  observers see it settle. Closing the client still interrupts running
  executions.
- **2.** `fetchQuery`, `prefetchQuery` and `ensureQueryData` follow the fetch
  that superseded the one they were waiting for. `cancelQueries` and
  `removeQueries` still interrupt the caller: cancelling a query is an
  interruption, and there is no typed error in `E` to report it with.
- **3.** An execution that ends with an interrupt-only cause returns to
  `idle`. It never reaches `error`, the error boundary or the observer's
  `onError` / `onSettled` (decision D7). `client.mutate` and `mutateEffect`
  are still interrupted, since the execution they wait for was.
- **4.** A query atom whose entry is removed while the client is shutting
  down keeps its last result instead of rebuilding.
- **5.** `resetQueries` also reloads active `"static"` queries that the reset
  left without data. Invalidation still never refetches static data.
- **6.** An entry that only holds its `initialData` adopts restored data,
  whether the restore happens before or after the entry is created. Data that
  was fetched or written is never replaced.
- **7.** Refreshing a query atom refreshes a small helper atom in the registry
  that was asked to, and its rebuild forces the refetch with that registry's
  client. The per-atom closure is gone.
- **8.** An observer with its own `staleTime` runs its own timer and notifies
  when that threshold passes.
- **9.** `reset()` reschedules gc (and polling) itself, since the exit of the
  fetch it drops is ignored.
- **10.** `QueryKey.toJsonKey` keeps `undefined` as a tagged value, so keys
  the cache keeps apart get different storage keys. Snapshots stored under the
  old string for such keys are not claimed and expire after `maxAge`.
